# Web app security

- Date: 2026-10-14
- Related: [ADR 0003](../adr/0003-on-device-processing-by-default.md),
  [spike-browser-wasm.md](spike-browser-wasm.md), `web/`, `cmd/cedolo-wasm`

The web app handles the most sensitive document most people own. Its promise
is that payslips never leave the device and nothing is kept. This document
lists what enforces that promise, how it was tested, and what it cannot
cover.

## What is protected and against what

| Threat | Protection |
| --- | --- |
| The page, a dependency or injected code sends data elsewhere | Content-Security-Policy: `default-src 'none'`, `connect-src 'self'`, no remote scripts, images, fonts, frames, plugins or form targets |
| A crafted PDF exploits a flaw in pdf.js | pdf.js runs in the page, not in a Web Worker, so the policy applies to it (`worker-src 'none'`); no fonts are handed to the browser (`disableFontFace`), no system fonts, no forms (XFA), no scripting, no canvas; pdf.js 6 has no `eval` path and the policy forbids `eval` anyway |
| Text from a PDF injects markup (item descriptions, contract, file names) | The page writes only with `textContent`; the report is generated by Go `html/template`, which escapes every value; injected handlers or scripts are also blocked by the policy |
| The report reaches the page or the network | The report runs in an `iframe` with `srcdoc` and `sandbox="allow-scripts"`: no same origin (no access to the page, storage or cookies), no navigation of the page, no popups, no forms, no downloads. It inherits the page's policy; its one inline script is allowed by hash (`report.ScriptHash`, tested against the rendered page) |
| Data stays on the device after use | Nothing is written to `localStorage`, `sessionStorage`, IndexedDB, the Cache API or cookies; there is no service worker; files are read into memory and dropped by "Start over" or by closing the page |
| A huge or hostile file freezes the page | Files over 20 MB or 50 pages, and more than 60 files at once, are refused before parsing; each document is extracted on its own and a panic in the Go core is recovered and reported for that file only; the extractor is fuzzed (`FuzzDocument`) |
| A password typed for a protected PDF leaks | It is passed to pdf.js only, kept in memory to try on the next protected file, and dropped by "Start over" or closing the page; the form is never submitted |
| Third parties learn about the visit | No analytics, fonts or CDNs; `no-referrer`; DNS prefetching off |
| A compromised dependency or build step | pdf.js pinned with its lockfile integrity hashes, installed with `--omit=optional --ignore-scripts`; only its built files and font data are shipped; GitHub Actions pinned to commit hashes, checkouts without persisted credentials where no push is needed; Dependabot proposes updates |

## How it was tested

`web/test/security.test.mjs` (CI) checks the built page: the policy and its
position, no remote sources, pdf.js in the page, the sandboxed frame, no
storage. `web/test/e2e.test.mjs` (CI) drives the built app in Chromium:
hostile file names, damaged, oversized, repeated and protected files, no
request outside the site, blocked fetch, workers and eval from the page and
the report frame, no storage afterwards, and the message for browsers that
cannot run it. Before those tests existed, the built app was also driven
by hand with hostile input (2026-10-14):

- A synthetic payslip with `<script>`, `<img onerror>` and `<svg onload>` in
  item descriptions and in the contract, and a file named
  `<img src=x onerror=alert(1)>.pdf`: shown as plain text, no handler or
  script created, no dialog.
- From the page: `fetch`, image beacons and form posts to another origin,
  `new Worker`, `eval`, injected inline scripts and handlers were all blocked
  (the other origin received no request).
- From the report frame: `fetch` to another origin, reading the page,
  `localStorage` and navigating the page were all blocked.
- A 51-page PDF and a 25 MB file were refused.
- After a session: no storage of any kind, no cookies, no service worker.

A worker loaded from a file was shown to ignore the page's policy and reach
another origin: the policy is set by a `<meta>` tag, because static hosting
such as GitHub Pages cannot send headers, and a worker only obeys the
headers of its own script. That is why pdf.js does not use one.

## Limits

These are not covered, and should not be claimed:

- **Trust in the code served.** The policy constrains mistakes and injected
  content, not the site itself: whoever controls the hosting, the repository
  or the build could serve different code. Top-level navigation, popups and
  WebRTC are not governed by Content-Security-Policy, so code running in the
  page could still send data out. The defence is review of what is
  published: open source, reproducible build, pinned dependencies.
- **Headers.** On GitHub Pages the policy can only be a `<meta>` tag:
  `frame-ancestors` (framing by other sites), reporting and other header-only
  protections are unavailable. Framing exposes no data, since files given to
  a framed copy stay in it. A host that can set headers should send the same
  policy as a header, plus `frame-ancestors 'none'`,
  `X-Content-Type-Options: nosniff` and `Cross-Origin-Opener-Policy: same-origin`.
- **The host sees visits.** GitHub logs the IP address and the static files
  requested, never the PDFs. Enforce HTTPS in the Pages settings.
- **The browser and the device.** Browser extensions with access to the page
  can read everything in it; a compromised device is out of scope. A
  downloaded report is an ordinary file on the device.
- **`style-src 'unsafe-inline'`** is needed by the report's styles and chart
  attributes. Injected markup cannot run script, but injected styles could in
  principle leak a little through CSS selectors to the same site only, since
  `img-src` and `connect-src` exclude other origins.
- **Memory.** Data stays in the page's memory until "Start over" or closing
  the tab; JavaScript cannot guarantee that memory is wiped.

## Serving it

- GitHub Pages: enable "Enforce HTTPS".
- Locally: `python3 -m http.server --bind 127.0.0.1`; without `--bind` the
  server is reachable from the whole network.
